# Architecture Decision Record

## Purpose

Document an architectural decision, its context, the alternatives considered, and the rationale behind the chosen approach.

## When Used

Use this template when an architecture decision affects system structure, maintainability, governance or the long-term evolution of the ForgeOS framework.

## Produced By

Forge-Architecture-Decision-Records

## Consumed By

* ForgeOS Maintainers
* Architects
* Contributors
* Future Maintainers

---

## Decision Title

**ADR-002: Separate the ForgeOS Framework from ForgeOS Project Documentation**

---

## Context

ForgeOS is both:

* a reusable engineering framework
* a software project that evolves over time

Most engineering work modifies the Framework itself by improving workflows, standards, agents, skills and templates.

However, some information represents the evolution of ForgeOS rather than the framework's current state. Examples include Architecture Decision Records (ADRs), roadmap planning, release planning and future enhancements.

Storing these documents within the Framework would mix immutable engineering knowledge with living project documentation.

---

## Decision

Introduce a dedicated **ForgeOS Project** folder within the repository.

The Framework remains the authoritative source of reusable engineering knowledge.

The ForgeOS Project folder stores living project documentation including:

* Architecture Decision Records
* Roadmap
* Product Backlog
* Release Notes
* Other project management artefacts

This folder complements the Framework but does not duplicate it.

---

## Alternatives Considered

### Store project documentation within the Framework

**Rejected**

This mixes framework knowledge with project history and weakens the separation between reusable engineering guidance and project evolution.

### Create a second ForgeOS project repository

**Rejected**

This introduces unnecessary complexity and duplication.

### Introduce a lightweight ForgeOS Project folder

**Selected**

This preserves a single repository while maintaining clear separation of responsibilities.

---

## Rationale

The Framework represents the current engineering operating system.

The ForgeOS Project folder captures the decisions, planning and history that explain how the framework evolves.

This approach keeps the Framework concise while preserving important historical context.

---

## Consequences

### Positive

* Clear separation of concerns.
* Framework remains the single source of engineering truth.
* Historical decisions remain discoverable.
* No duplication of framework documentation.
* Simplified repository structure.

### Trade-offs

* Introduces an additional top-level folder.
* Contributors must distinguish between framework knowledge and project documentation.
