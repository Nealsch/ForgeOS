# ADR-009: Framework Binding & Consumption Model

**Status:** Accepted

## Context

ForgeOS concepts work, but nothing operationalises how a project consumes the Framework. Adoption simulation (2026-09-07, recorded as WI-002) confirmed that without a sanctioned binding mechanism:

* Projects risk **version drift** — no way to state which Framework release a project follows.
* The read-only/independent-versioning rule for the Framework is **unexportable** — nothing prevents a project from forking or copying the Framework and diverging.
* Adoption is **ad hoc** — every project invents its own attachment procedure.

Candidate mechanisms evaluated:

| Option | Verdict | Rationale |
|--------|---------|-----------|
| Copy the Framework into the project | **Forbidden** | Guarantees drift; breaks the single source of engineering truth. |
| Git submodule | **Rejected** | Couples the project's git history to the Framework repo's commits; awkward pin semantics (commit, not release); poor experience for non-git-native consumers and AI agents. |
| Sibling clone + pinned pointer | **Accepted** | The Framework lives as an independent clone beside the project; the project records a pointer to a Framework **release tag**. Clean separation, independent versioning, explicit upgrade action. |

## Decision

A project binds to the ForgeOS Framework via a **sibling clone with a pinned release-tag pointer**:

1. The Framework repository is cloned to a sibling location of the project directory (e.g. `../ForgeOS`).
2. The project records, in its own documentation (Project Definition metadata), the **Framework release tag** it is bound to (e.g. `v1.0.1`).
3. All Framework references from project docs and AI runtime configuration resolve through that sibling path.
4. **Copying or forking the Framework into a project is forbidden.** The Framework is consumed read-only.
5. Upgrading the binding is an explicit, recorded action: update the sibling clone to the new release tag, update the pin record, and review the Framework compatibility notes — including the risks/rewards statement for any Breaking changes, which the Product Owner must deliberately accept before upgrade.

## Consequences

### Positive

* Framework remains independently versioned and released; no drift.
* Every project can state its exact Framework version by inspection (pin record).
* Updates are deliberate and reviewable, never accidental.
* The Framework layer never absorbs project-specific rules.

### Negative

* Requires the sibling directory convention to be documented and followed per machine.
* Projects must perform an explicit step to adopt Framework updates.

## Architectural Principles

* The Framework is a **single source of engineering truth** and is consumed, never embedded.
* Project-specific constraints belong to **Project Documentation**, never the Framework.
* The binding is **documentation-level**, not a build-level dependency: nothing in a project's build or runtime may execute from inside the Framework.
* Framework upgrade compatibility is governed by Framework compatibility Governance (`Framework/03-Governance/compatibility.md`), including the **Compatibility Preference and Upgrade Review** policy: backwards compatibility is preferred but never privileged over functional gains; Breaking changes carry a documented risks/rewards statement reviewed and approved by the Product Owner, so projects are never stranded on stale pins by default.
