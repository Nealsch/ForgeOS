## Decision Title

**ADR-005: Introduce Platform-Independent Work Item Management**

---

## Context

ForgeOS supports AI-assisted software development through a structured Software Development Lifecycle (SDLC). Work entering the SDLC may originate from a variety of external systems including issue trackers, project management tools, customer feedback systems and support platforms.

Initially, GitHub Issues were identified as the primary source of work for ForgeOS. However, designing the framework around GitHub would introduce unnecessary coupling to a single platform and conflict with the ForgeOS principles of platform independence and reusability.

Furthermore, externally managed work items typically lack the engineering context required for structured software development. Before work can enter the SDLC it must be analysed, enriched, prioritised and aligned with ForgeOS engineering practices.

ForgeOS therefore requires a platform-independent mechanism for managing work before engineering activities begin.

---

## Decision

ForgeOS introduces **Work Item Management** as a core Collaboration Orchestration capability.

Work Item Management is responsible for synchronising, enriching, prioritising and preparing work for execution within the ForgeOS Software Development Lifecycle.

The Framework shall use the generic term **Work Item** to describe all units of work regardless of their source.

Examples include:

* Bug reports
* Feature requests
* Enhancements
* Technical debt
* Maintenance activities
* Security findings
* Documentation improvements
* Customer requests
* Operational tasks

Platform-specific concepts such as GitHub Issues, Jira Issues or Azure DevOps Work Items are implementation details managed by the Tooling layer.

---

## Responsibilities

Work Item Management is responsible for:

* Synchronising work with external tracking systems.
* Detecting completed work requiring external updates.
* Closing completed external work items where appropriate.
* Importing new work.
* Detecting duplicate and related work.
* Enriching imported work with ForgeOS engineering metadata.
* Determining engineering priority.
* Producing the local engineering backlog.
* Presenting recommendations to the Product Owner for approval.

Work Item Management does **not** perform engineering implementation.

Once a Work Item has been approved, responsibility passes to the ForgeOS Workflow and the appropriate specialist Agents.

---

## Work Item Lifecycle

Every Work Item follows the same orchestration process before entering the SDLC.

```text
Synchronise Completed Work
        ↓
Update External Platform
        ↓
Close External Work Items
        ↓
Fetch Outstanding Work
        ↓
Validate Imported Work
        ↓
Detect Duplicates
        ↓
Identify Related Work
        ↓
Enrich Engineering Context
        ↓
Determine Engineering Priority
        ↓
Generate Local Backlog
        ↓
Product Owner Approval
        ↓
Enter SDLC
```

---

## Engineering Enrichment

Imported Work Items shall be transformed into ForgeOS engineering artefacts.

In addition to externally supplied information, ForgeOS may enrich each Work Item with metadata including:

* Business impact
* User impact
* Security impact
* Technical risk
* Implementation complexity
* Dependencies
* Related Work Items
* Affected components
* Required Agents
* Required Skills
* Applicable Standards
* Synchronisation status
* External tracking references

This enrichment enables structured engineering decisions throughout the SDLC.

---

## Engineering Priority

ForgeOS determines implementation priority using engineering considerations rather than relying solely on external platform priorities.

Priority recommendations should consider factors including:

* Business value
* User impact
* Security impact
* Technical risk
* Dependencies
* Implementation complexity
* Strategic importance

The AI Program Manager presents the recommended implementation order to the Product Owner.

The Product Owner remains responsible for approving the final implementation sequence.

---

## Tooling Separation

The ForgeOS Framework defines **how** Work Items are managed.

The Tooling layer defines **how** external platforms are integrated.

For example:

```text
Framework
└── Collaboration Orchestration
    └── Work Item Management

Tooling
└── Platforms
    ├── GitHub
    ├── Jira
    ├── Azure DevOps
    └── GitLab
```

Each platform adapter is responsible for translating between the platform's native work-item model and the ForgeOS Work Item model.

---

## Alternatives Considered

### Base ForgeOS on GitHub Issues

**Rejected**

This couples the framework to a single platform and reduces future portability.

---

### Implement separate orchestration for each platform

**Rejected**

This duplicates engineering logic across multiple integrations and increases maintenance effort.

---

### Introduce a platform-independent Work Item abstraction

**Selected**

This maintains a clean separation between engineering processes and platform integrations while supporting future expansion.

---

## Rationale

Work Item Management establishes a single, consistent intake process for all engineering work entering ForgeOS.

By separating orchestration from platform integration, the framework remains independent of external tooling while enabling rich engineering analysis before implementation begins.

This approach also ensures that engineering prioritisation is based on technical and business considerations rather than the capabilities or terminology of a particular issue tracking system.

---

## Consequences

### Positive

* Maintains platform independence.
* Supports multiple external work-item systems.
* Eliminates duplicated orchestration logic.
* Produces a richer engineering backlog than external platforms alone.
* Enables consistent prioritisation across all projects.
* Provides a repeatable entry point into the ForgeOS SDLC.
* Simplifies future platform integrations.

### Trade-offs

* Requires platform adapters to translate between external systems and the ForgeOS Work Item model.
* Introduces an enrichment step before engineering work can begin.

## Completion Criteria

* Work Item Management is introduced within the Collaboration Orchestration layer.
* The Framework consistently uses the term **Work Item**.
* Platform-specific implementations are moved to the Tooling layer.
* Imported Work Items are enriched using ForgeOS engineering metadata.
* Engineering priority is determined before work enters the SDLC.
* The Product Owner approves the implementation order before execution begins.
