# ADR-008: Codebase Analysis Tooling Capability & Graphify Integration Contract

**Status:** Accepted

## Context

**ADR-007** established that *Codebase Analysis is an Agent, not a Skill*, and that *Graphify is a preferred implementation of a codebase analysis capability* while *ForgeOS remains independent of any specific analysis tool*.

ADR-007 captured the **architectural intent** correctly. However, it did not define the **integration contract** required to make that independence enforceable in practice. Without that contract, two risks emerge:

1. **Platform coupling.** Graphify is currently distributed as a *Claude Code skill*, and parts of its extraction (PDF, images) rely on *Claude vision*. Naive integration would leak Claude Code specifics up into the Framework, violating the platform-independence principle in `AGENTS.md` (Core Principles) and the authority hierarchy.
2. **Decision leakage.** Graphify produces interpretive outputs (god nodes, surprising connections, suggested questions). These are *analysis signals*, not *engineering conclusions*. Without an explicit boundary, Tooling outputs could be mistaken for Framework-owned engineering decisions, contradicting `Tooling/README.md` ("Tooling never owns engineering decisions").

ForgeOS has already solved the structurally identical problem twice:

* **ADR-005 / GitHub adapter** — *"adapter owns mechanics, Framework owns decisions."*
* **MCP adapter** (`Tooling/02-Adapters/MCP/README.md`) — a vendor-neutral protocol, explicitly the *preferred* integration path, which Graphify already supports natively via `graphify --mcp`.

This ADR applies the same discipline to codebase analysis tooling.

## Decision

A **Codebase Analysis Tooling Capability Contract** is introduced as the platform-neutral interface between the Framework (which owns the engineering outcome) and any external codebase analysis tool (which owns the analysis mechanics).

**Graphify** is the first concrete implementation of that contract. The contract guarantees that Graphify can be replaced or supplemented by any future tool that satisfies the same interface, without changes to the Codebase Analyst Agent, the Skills it invokes, or any ForgeOS Standard.

The contract lives in the Tooling layer at `Tooling/03-Capabilities/Codebase-Analysis-Capability.md` and is the single source of truth for "what a codebase analysis tool must provide to ForgeOS".

## The Codebase Analysis Capability Contract

Any tool satisfying this contract must provide:

### Inputs

* A target repository path (the **project-under-development**, never the ForgeOS Framework itself).
* Optional: a pre-existing graph snapshot for incremental refresh.

### Outputs

* A **knowledge graph** — a persistent representation of nodes (concepts, modules, functions) and edges (relationships) with each edge tagged with a **confidence label**:
  * `EXTRACTED` — relationship explicitly present in source (e.g. an import, a call).
  * `INFERRED` — reasonable deduction (e.g. call-graph second pass).
  * `AMBIGUOUS` — uncertain; flagged for human review.
* An **analysis report** identifying:
  * high-degree concepts ("god nodes"),
  * ranked surprising connections,
  * suggested questions the graph is positioned to answer.
* Optional exports: interactive visualisation, Obsidian vault, wiki, SVG/GraphML, Neo4j cypher.

### Quality Signals (mandatory)

* **Confidence labels** on every edge. No relationship may be presented as a fact unless tagged `EXTRACTED`.
* **Freshness indicator** on the graph (build timestamp / commit SHA), because the graph is a **snapshot**, not live state.
* **Deterministic AST extraction** for supported code languages (Graphify uses tree-sitter) independent of any LLM.
* **Local execution.** The tool must run entirely on the engineer's machine; no mandatory external server.

### Integration Surface

The tool must be consumable by ForgeOS through at least one of:

* **MCP server** (preferred) — local stdio server answering `query` / `path` / `explain` against the persisted graph.
* **CLI / library** — for batch analysis, report generation and metrics.
* **Prompt-Based fallback** — consuming the report file directly when a platform exposes no tool surface.

## Graphify Integration Profile

Graphify satisfies the contract as follows:

| Contract requirement | Graphify implementation |
| --- | --- |
| Knowledge graph with confidence labels | `graphify-out/graph.json`; edges tagged `EXTRACTED` / `INFERRED` / `AMBIGUOUS` |
| Analysis report | `graphify-out/GRAPH_REPORT.md` |
| Deterministic AST extraction | tree-sitter pass for code; LLM (Claude) only for docs, PDFs, images |
| Local execution | No server, no Neo4j; runs entirely locally |
| MCP surface | `graphify --mcp` (`serve.py` → stdio MCP server over a pre-built `graph.json`) |
| CLI / library | `pip install graphifyy` (CLI) + importable Python library |
| Incremental refresh | `graphify --update` (SHA256 cache) and `graphify hook install` (post-commit) and `graphify --watch` |

### Platform-Coupling Containment Rule

Graphify's platform couplings — its Claude Code skill wrapper and Claude vision dependency — are **contained entirely inside its Tooling profile** (`Tooling/01-Platforms/Graphify/README.md`). They must never be referenced from:

* The Codebase Analyst Agent definition.
* Any Skill the Agent invokes.
* Any Workflow, Standard, or Governance document.
* The Capability Contract itself.

The Claude-Code-specific `/graphify` slash command is **not** a ForgeOS concept; it is one adapter's convenience entry point. The Framework addresses the Capability Contract, not Graphify's UI.

### Deployment & Target-Codebase Binding

* **Where the MCP server runs:** locally, as a stdio subprocess spawned by the AI platform's MCP client (Cline, Claude Code, VS Code Agent, Cursor), reading `graphify-out/graph.json` from disk.
* **Which codebase is analysed:** the **project-under-development** (the software being engineered with ForgeOS), never the ForgeOS Framework itself. The graph binds to the project.
* **Where artefacts live:** `graphify-out/` lives **inside the project**, with the persistent `graph.json` optionally stored under the project's `.ai/knowledge/` directory. The ForgeOS repo must never contain a `graphify-out/` directory; it is added to the root `.gitignore` defensively.
* **Meta / onboarding use:** running Graphify over ForgeOS itself is permitted purely as a demonstration and onboarding aid; it is not the primary use case and produces no Framework artefact.

## Adapter Boundary (no duplication)

This boundary mirrors the Platform Adapter Contract in `Tooling/README.md` and the GitHub adapter in `Tooling/01-Platforms/GitHub/README.md`.

| Owned by the Capability Contract + Graphify profile (Tooling) | Owned by the Framework (Codebase Analyst Agent + Skills) |
| --- | --- |
| Graph build, extraction, clustering, analysis mechanics | Deciding *whether* analysis is required |
| MCP server / CLI / library invocation | Selecting the analysis technique |
| Confidence label production | Interpreting results into engineering conclusions |
| Graph + report file production | Identifying technical debt and risks |
| Freshness / cache mechanics | Producing the Architecture Assessment artefact |
| Graphify-specific security (URL/path/label validation) | Approving any resulting Work Items |

Adding or replacing Graphify must never require changes to the Codebase Analyst Agent, the Skills it invokes, the Workflow, or any Standard.

## Consequences

### Positive

* Makes ADR-007's intent **implementable and enforceable** without weakening it.
* Preserves platform independence: Graphify's Claude Code coupling is confined to the Tooling layer.
* Preserves the authority hierarchy: Tooling produces signals; the Framework owns engineering conclusions.
* Guarantees replaceability: any future tool satisfying the contract plugs into the same Agent and Skills.
* Reuses the proven adapter discipline of ADR-005 / GitHub and the preferred MCP adapter.
* Establishes a freshness model so a stale graph is never mistaken for live source.

### Negative

* Introduces one new Tooling capability contract and one new tooling profile that must be maintained.
* The platform-coupling containment rule must be policed on every change to the Graphify profile.
* Engineers must understand the snapshot nature of the graph and refresh it deliberately.

## Architectural Principles

This ADR reinforces existing ForgeOS principles; it introduces no new ones:

* **Platform independence** (AGENTS.md → Core Principles).
* **Tooling never owns engineering decisions** (`Tooling/README.md`).
* **Adapter owns mechanics; Framework owns decisions** (ADR-005).
* **MCP is the preferred adapter when supported** (`Tooling/02-Adapters/MCP/README.md`).
* **Agents own outcomes; Skills provide capability; Tooling integrates** (ADR-007).

## Rationale

ADR-007 said *what* Codebase Analysis is (an Agent) and *what Graphify is* (a preferred tool, not a Skill). It left *how* the two connect without coupling ForgeOS to Claude Code unspecified.

ForgeOS already has a proven pattern for exactly this situation: define a platform-neutral contract in the Framework/Tooling boundary, satisfy it with a concrete adapter, and confine all platform specifics to the adapter. Applying that pattern to codebase analysis lets ADR-007 stand unchanged while giving engineers a real, usable, replaceable capability today.
