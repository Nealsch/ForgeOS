## Decision Title

**ADR-001: Introduce Collaboration Orchestration as a Core ForgeOS Framework Component**

---

## Context

ForgeOS was originally structured around the following framework components:

* Workflow
* Standards
* Agents
* Skills
* Templates

As the framework evolved, AI-assisted engineering capabilities such as Task Routing, Context Loading, Agent Collaboration, Session Management and Knowledge Management were introduced.

These capabilities exposed a missing architectural layer.

The Software Development Lifecycle (Workflow) defines **when** engineering work occurs, while Skills define **how** engineering activities are performed. However, neither component defines how a human request is transformed into a coordinated engineering activity.

A second source of ambiguity emerged from the widespread use of the term **Agent** within AI tooling.

Many AI products—including Cline, Claude Code, Cursor and similar tools—describe themselves as *AI Agents*. Within ForgeOS, however, an **Agent** represents an engineering role such as Architect, Backend Engineer or Quality Engineer.

Without explicitly separating these concepts:

* AI execution logic becomes distributed across multiple Skills.
* Responsibility for selecting Skills, Standards and Templates becomes ambiguous.
* Human interaction patterns are not consistently defined.
* The distinction between execution software, language models and engineering roles becomes unclear.
* The relationship between the human, AI and the ForgeOS framework remains implicit rather than architectural.

To support consistent human–AI collaboration, ForgeOS requires a dedicated orchestration model that coordinates framework components while remaining independent of any specific execution environment or Large Language Model (LLM).

---

## Decision

Introduce **Collaboration Orchestration** as a first-class component of the ForgeOS Framework.

Collaboration Orchestration is responsible for transforming human engineering intent into structured engineering execution by coordinating the existing framework components.

It acts as the execution layer between the human and the ForgeOS framework.

ForgeOS formally distinguishes the following concepts:

| Concept                         | Responsibility                                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **Human**                       | Defines objectives, priorities, approvals and engineering decisions.                                    |
| **Execution Environment**       | The software through which the human interacts with ForgeOS (e.g. Cline, Claude Code, Cursor, ChatGPT). |
| **LLM**                         | Provides reasoning and language capabilities (e.g. Claude, GPT, Gemini, GLM).                           |
| **Collaboration Orchestration** | Coordinates execution of engineering work using the ForgeOS framework.                                  |
| **ForgeOS Agent**               | Represents an engineering role such as Architect, Backend Engineer or Quality Engineer.                 |
| **Skill**                       | Provides a reusable engineering capability.                                                             |

The Collaboration Orchestration layer is responsible for:

* Interpreting engineering requests.
* Routing work to the appropriate Workflow phase.
* Selecting the appropriate ForgeOS Agent or Agents.
* Selecting the required Skill or Skills.
* Loading applicable ForgeOS Standards.
* Loading applicable external standards.
* Selecting required Templates.
* Loading relevant project context.
* Loading reference examples when beneficial.
* Coordinating execution.
* Producing engineering artifacts.
* Maintaining engineering traceability.

The orchestration layer defines **how humans and AI collaborate** but does not replace the responsibilities of the Workflow, ForgeOS Agents, Skills or Standards.

---

## Alternatives Considered

### Option 1 – Continue Using Skills for Orchestration

Allow Skills such as Forge-Task-Routing and Forge-Context-Loading to collectively define orchestration behaviour.

**Rejected**

This distributes orchestration responsibilities across multiple Skills, creating duplicated logic, unclear ownership and inconsistent execution.

---

### Option 2 – Extend the Workflow

Expand the Workflow to include AI execution and context management.

**Rejected**

The Workflow defines the Software Development Lifecycle and answers **when** engineering work occurs.

AI execution is independent of SDLC phases and therefore represents a separate architectural concern.

---

### Option 3 – Make ForgeOS Agents Responsible for Orchestration

Require each ForgeOS Agent to determine which Skills, Standards and Templates to use.

**Rejected**

ForgeOS Agents represent engineering roles and responsibilities.

Embedding orchestration logic within Agents would tightly couple execution behaviour to individual roles, reducing reuse and increasing complexity.

---

### Option 4 – Introduce Collaboration Orchestration as a Framework Component

Create a dedicated framework component responsible for coordinating human–AI collaboration.

**Selected**

This provides a clear separation of responsibilities while preserving the existing architecture.

---

## Rationale

Collaboration Orchestration establishes a single responsibility for engineering execution coordination.

It clearly separates:

* **Workflow** — defines when engineering work occurs.
* **Execution Environment** — hosts the interaction between the human and the AI.
* **LLM** — provides reasoning capabilities.
* **Collaboration Orchestration** — coordinates engineering execution.
* **ForgeOS Agents** — represent engineering roles.
* **Skills** — define reusable engineering capabilities.
* **Standards** — define quality expectations.
* **Templates** — define engineering artifact structure.

This architecture:

* Removes ambiguity from AI execution.
* Clearly separates execution software from engineering roles.
* Supports efficient context loading.
* Improves maintainability.
* Enables consistent engineering behaviour across different AI platforms.
* Preserves technology independence.
* Allows execution environments and LLMs to evolve independently of ForgeOS.
* Allows orchestration capabilities to evolve without affecting engineering Skills.

It establishes Collaboration Orchestration as the architectural contract between the human and the ForgeOS framework.

---

## Consequences

### Positive

* Clear separation of framework responsibilities.
* Consistent human–AI collaboration model.
* Execution environments can be replaced without changing ForgeOS.
* LLMs can be replaced without changing ForgeOS.
* Simplified Context Loading and Task Routing.
* Improved scalability as additional Skills, Standards and Templates are introduced.
* Framework becomes independent of specific tools such as Cline, Claude Code, Cursor or ChatGPT.
* Framework becomes independent of specific LLMs such as Claude, GPT, Gemini or GLM.
* Easier onboarding for both human engineers and AI systems.
* Stronger architectural identity for ForgeOS as an Engineering Operating System.

### Trade-offs

* Requires updates to existing framework documentation.
* Introduces an additional framework component that contributors must understand.
* Existing AI-Assisted Engineering documentation must be aligned with the new architecture.
* ForgeOS terminology differs intentionally from the terminology used by many AI tooling vendors.

## Completion Criteria

* Collaboration Orchestration is established as a first-class ForgeOS framework component.
* Framework documentation reflects the updated architecture.
* Responsibilities between Workflow, Collaboration Orchestration, Execution Environment, LLM, ForgeOS Agents, Skills, Standards and Templates are clearly separated.
* AI orchestration behaviour is defined independently of engineering capabilities.
* ForgeOS Agents remain engineering roles rather than software components.
* Execution Environments and LLMs remain interchangeable implementation choices.
* Existing Skills remain focused on capabilities rather than execution coordination.
* Future framework components can integrate through the Collaboration Orchestration layer without modifying the SDLC.
