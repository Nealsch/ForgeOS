# ForgeOS Documentation Standard

## Purpose

The Documentation Standard defines the enduring principles for creating and maintaining engineering documentation within ForgeOS.

Documentation is considered a first-class engineering artefact. It preserves knowledge, enables collaboration between humans and AI agents, and provides the traceability required to understand, maintain and evolve software throughout its lifecycle.

These standards apply regardless of project size, technology stack or development methodology.

---

# Documentation Philosophy

Software is more than source code.

A successful project preserves not only **what** was built, but also **why**, **how** and **when** decisions were made.

Documentation should eliminate uncertainty, reduce reliance on tribal knowledge and support long-term maintainability.

---

# Documentation Principles

## 1. Documentation Is Part of the Product

Documentation is not optional or an afterthought.

A feature is not considered complete until its required documentation has been updated.

---

## 2. One Source of Truth

Every piece of information should have a single authoritative location.

Avoid duplicated information that can become inconsistent over time.

Where appropriate, reference existing documentation rather than copying it.

---

## 3. Record Decisions, Not Just Outcomes

Engineering decisions have long-term consequences.

Significant decisions, assumptions, constraints and trade-offs should be documented so future contributors understand the reasoning behind the solution.

---

## 4. Keep Documentation Close to the Work

Documentation should evolve alongside the project.

When the implementation changes, the corresponding documentation should be reviewed and updated as part of the same change.

---

## 5. Write for Humans and AI

Documentation should be:

* clear
* structured
* concise
* unambiguous
* easy to navigate

Well-structured documentation improves both human understanding and AI-assisted development.

---

## 6. Prefer Structure Over Narrative

Use consistent headings, terminology and document structures.

Predictable documentation enables faster navigation and more reliable retrieval by both developers and AI agents.

---

## 7. Preserve Knowledge

Important knowledge should never exist only in conversations, chat histories or individual memory.

If knowledge is likely to be needed again, it should be captured in the appropriate project documentation.

---

## 8. Documentation Must Remain Accurate

Outdated documentation is worse than missing documentation.

When documentation no longer reflects reality, it should be updated or removed.

---

## 9. Traceability Matters

Documentation should allow readers to understand the relationship between:

* business objectives
* requirements
* architecture
* implementation
* testing
* deployment
* operational decisions

This traceability supports maintenance, auditing and future development.

---

## 10. Documentation Should Explain Intent

Documentation should explain:

* why something exists
* what problem it solves
* important assumptions
* known constraints
* significant trade-offs

Implementation details belong in the code where appropriate.

---

# Relationship to Other Standards

This standard defines **how engineering knowledge is recorded**.

It complements:

* Architecture Standards
* Coding Standards
* Security Standards
* Testing Standards
* Deployment Standards

Together these standards ensure that software remains understandable throughout its lifecycle.

---

# Immutable Engineering Knowledge

The Documentation Standard defines enduring engineering expectations.

Project-specific documents, templates and project records belong within the individual project created from the ForgeOS Project Template, not within the ForgeOS framework itself.

---

# ForgeOS Principle

Documentation preserves engineering knowledge.

Good documentation enables software to be understood, trusted and improved long after the original implementation has been completed, ensuring that knowledge remains an asset rather than a dependency on individual people.
